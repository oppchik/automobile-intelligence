# AuInt — «Чинить или продавать?»

## Принцип проекта

Автовладелец, столкнувшийся с поломкой, вводит данные о машине (марка,
модель, год, пробег, регион, состояние до поломки) и описывает проблему
текстом, отмечает категории повреждений и/или загружает фото. Дальше сервис:

1. **Определяет категории повреждений** — шесть независимых групп (кузов,
   оптика, электроника, подвеска, двигатель, окраска) плюс скрытая категория
   «силовой каркас/рама», включаемая только автоматически по тексту описания.
2. **Считает смету ремонта** в трёх вариантах — официальный дилер,
   независимый сервис, б/у запчасти.
3. **Ищет запчасти** у нескольких продавцов с фильтрами по цене, состоянию и
   расстоянию, с отслеживанием цены.
4. **Оценивает рыночную стоимость автомобиля** — в хорошем состоянии, «как
   есть» и после ремонта.
5. **Даёт рекомендацию** — «чинить», «продать как есть» или «нужна очная
   диагностика» — и показывает точку безубыточности ремонта.
6. Сохраняет каждый расчёт в историю, привязанную к анонимному
   идентификатору сессии устройства (полноценная аутентификация — в планах).

Это MVP: расчёты сметы, цен на запчасти и рыночной стоимости построены на
демонстрационных формулах и справочных таблицах (`backend/app/data.py`,
`backend/app/engine.py`), а не на реальном парсинге объявлений; нейросеть
по фото определяет только тяжесть повреждения (см. «Распознавание по фото»).

## Смета ремонта

Смета считается в трёх вариантах: официальный дилер, независимый сервис,
б/у запчасти. Для каждого варианта:

- **Работы** = нормо-часы по категориям повреждений × ставка нормо-часа.
  Ставка = 2 000 ₽ × региональный коэффициент × коэффициент класса автомобиля
  × множитель варианта (у дилера 1,7, у остальных 1,0).
- **Запчасти и материалы** = базовая цена × коэффициент класса автомобиля ×
  наценка варианта (у дилера 1,35); в варианте «б/у запчасти» берутся цены
  б/у деталей, расходные материалы остаются новыми.
- **Диагностика** = 4 500 ₽ × региональный коэффициент.
- **Непредвиденные расходы** = 12% от суммы запчастей и работ.

`POST /api/estimate` принимает тот же запрос, что и `/api/calculate`, и
возвращает расшифровку по каждому варианту: строки работ (часы, ставка,
сумма), строки запчастей и материалов, итоговые статьи, экономию относительно
дилера и самый выгодный вариант. Суммы строк округлены до рубля так, что
всегда в точности складываются в итог. Если API недоступен, интерфейс считает
то же самое локально (`buildEstimate` в `frontend/src/lib/engine.js`).

Проверка: `cd backend && python -m unittest` и `cd frontend && npm test`.

## Распознавание по фото

Фото из формы уходят в `POST /api/vision/severity` (multipart, поле `photos`,
до 6 файлов JPEG, PNG или WebP по 8 МБ). Модель из `ml/` (EfficientNet-B0 и
логистическая регрессия) возвращает тяжесть повреждения — лёгкая, средняя или
тяжёлая — и уверенность; по нескольким фото вероятности усредняются.
Повреждённые детали модель не определяет: категории отмечает пользователь.

- **Ручная корректировка.** Результат можно изменить; итоговое значение уходит
  в расчёт как `photo_severity` и заменяет прибавку к тяжести за количество фото
  (лёгкая +0, средняя +0,06, тяжёлая +0,12). Без значения расчёт прежний.
- **Низкая уверенность** (ниже порога `tau` = 0,55 из `ml/models`): ничего не
  подставляется, интерфейс просит выбрать тяжесть вручную.
- **Защита от сбоев.** Эндпоинт всегда отвечает 200 со статусом `ok`,
  `low_confidence`, `unavailable`, `timeout`, `busy`, `error` или `rejected`;
  при любом статусе, кроме `ok`, интерфейс предлагает ручной выбор. Проверяются
  формат, размер и читаемость файлов; модель грузится лениво, неудачная загрузка
  не повторяется 60 секунд; инференс идёт в одном рабочем потоке с лимитом 20 с и
  очередью из двух запросов; ответ модели проверяется на корректность. Если
  сервера нет вовсе, интерфейс тоже переходит на ручной выбор.
- **Включение модели.** Без неё бэкенд работает в ручном режиме (так ведёт себя
  текущий Docker-образ). Для запуска: `pip install torch --index-url
  https://download.pytorch.org/whl/cpu`, затем `pip install -r
  backend/requirements-ml.txt`; веса (около 20 МБ) скачиваются при первом
  запросе в `ml/data/cache` с проверкой контрольной суммы.

Проверка: `cd backend && python -m unittest` (тест реальной модели
пропускается, если нет torch и весов) и `cd frontend && npm test`.

## Карта продавцов запчастей

Вкладка «Карта» показывает точки продавцов выбранного города на интерактивной
карте (Leaflet, подложка OpenStreetMap) и рядом список с теми же точками.
Поиск по детали или OEM-коду, фильтры по состоянию, доставке и возрасту цены,
сортировка по цене и расстоянию. Клик по пину или по карточке открывает условия
получения (самовывоз и часы работы, срок и стоимость доставки), источник цены и
дату цены с пометкой «Свежая цена», «Актуальна» или «Могла устареть» (до 3, до
7 и больше 7 дней). Источник и дату можно скрыть переключателем. Кнопка
«Выбрать точку покупки» запоминает выбор в браузере. «Рядом со мной»
пересчитывает расстояния от геопозиции, но только если пользователь не дальше
100 км от выбранного города.

`GET /api/sellers?region=...` возвращает центр города и точки продавцов:
координаты, расстояние до центра, самовывоз, доставку, источник, дату и возраст
цены. `GET /api/parts` теперь отдаёт у каждого предложения те же расстояние,
доставку, источник и дату: это свойства продавца, а не пары «деталь — продавец».
Все продавцы, условия, источники и даты демонстрационные, положение точек
условное (смещение от центра города по расстоянию и направлению).

Защита от сбоев: если библиотека карты не загрузилась, показываются список и
условия; если не загружаются тайлы, пины остаются на нейтральном фоне с
предупреждением; если геолокация недоступна или пользователь далеко от города,
расстояния считаются от центра; если сервера нет, используются локальные
демо-данные. Офлайн-движок считает хэш иначе, чем бэкенд, поэтому его точки и
цены отличаются от серверных. Для постоянной нагрузки вместо публичных тайлов
OpenStreetMap нужен собственный или коммерческий провайдер подложки.

## Советчик: графики, пояснения и пересчёт

Под блоком «Три сценария» на вкладке «Расчёт» стоит карточка «Советчик: затраты и
выгоды». Она берёт стоимость авто «как есть», цену после ремонта и стоимость
выбранного варианта ремонта и считает три сценария моделью
`backend/app/financial_advisor.py`: продать как есть, отремонтировать и продать,
отремонтировать и эксплуатировать. Условия можно менять: цель (деньги сейчас или
ездить дальше), срок владения от 1 до 10 лет, бюджет на ремонт, расходы на
владение в год, расходы на транспорт взамен и осторожность вывода. Любое изменение
пересчитывает карточку через 250 мс.

Карточка показывает рекомендацию с причиной и отрывом лучшего сценария от
второго, график затрат и выгод (доходы вправо, затраты влево, точка итога),
график итога по годам владения и раскрывающийся блок «Как посчитано» с формулой
и статьями по каждому сценарию. Кнопка «Сохранить расчёт в историю» записывает
условия и итоги советчика в историю. Сценарий «ремонт и эксплуатация» считается
только при указанных расходах на транспорт взамен; без них советчик просит
данные. Допущения (расходы на продажу 1%, потеря стоимости 12% в год, ставка
дисконтирования 8%) указаны под графиками и не настраиваются.

`POST /api/financial-advice` дополнен полями `breakdown` (статьи по сценариям),
`timeline` (итог по годам) и `comparison` (лучший и второй сценарий, отрыв и порог
осторожности); прежние поля и значения не менялись. Без сервера тот же расчёт
выполняет `frontend/src/lib/advisor.js`. Блок «Три сценария» выше считается своей
упрощённой моделью без расходов на продажу и дисконтирования, поэтому суммы и
рекомендации двух блоков могут отличаться.

## Личный кабинет и история

Вкладка «Кабинет»: регистрация по email и паролю (от 8 символов), вход, выход.
Пароль хранится в виде PBKDF2-SHA256 с солью, сессия живёт 30 дней, в базе лежит
только хэш токена. После входа история расчётов хранится в базе за аккаунтом и
доступна с любого устройства; расчёты, сделанные до входа, привязываются к
аккаунту при регистрации или входе. Без аккаунта история по-прежнему привязана к
анонимному идентификатору браузера.

В истории у каждой записи есть «Пересчитать» (подставляет автомобиль в форму и
сразу считает заново по текущим данным) и «Удалить».

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`,
  `GET /api/auth/me`: токен передаётся заголовком `Authorization: Bearer ...`.
- `GET /api/history?limit=...`, `POST /api/history`, `DELETE /api/history`,
  `DELETE /api/history/{id}`: с токеном работают с записями аккаунта, без токена с
  записями анонимной сессии (`session_id`).
- Таблицы `users`, `auth_sessions`; в `history_entries` добавлены `user_id` и
  `advisor` (условия и итоги советчика). Колонки добавляются в существующую базу
  при старте (`ensure_columns`), миграций Alembic в проекте нет.

Вход работает только при доступном сервере. Ограничения попыток входа, подтверждения
email и восстановления пароля нет; в проде нужны HTTPS и сужение CORS.

## Стек

- React 18 + Vite 5 (фронтенд), Cirrus-компоненты (кнопка, табы, поиск,
  чекбоксы), чёрно-бело-серая палитра с точечными функциональными цветами.
- FastAPI + SQLAlchemy (бэкенд): SQLite локально, PostgreSQL в Docker.
- PWA: манифест, service worker, устанавливается на домашний экран.
- Docker Compose: `db` (Postgres) + `api` (FastAPI) + `web` (Nginx).

Фронтенд всегда сначала обращается к API; если бэкенд недоступен, расчёт
бесшовно переключается на локальный офлайн-движок (`frontend/src/lib/engine.js`,
формулы продублированы 1:1 с бэкендом).

```
├── backend/

│       ├── models.py     ORM: история расчётов, пользователи, сессии, отслеживаемые запчасти
│       ├── schemas.py    Pydantic-схемы запросов/ответов
│       └── main.py       FastAPI-приложение и все эндпоинты
├── frontend/
│   └── src/
│       ├── components/   cirrus.jsx, Header.jsx, CalcPage.jsx, AdvisorCard.jsx, Charts.jsx, EstimateDetails.jsx, PartsPage.jsx, HistoryPage.jsx, AccountPage.jsx, ui.jsx
│       └── lib/          api.js (клиент с офлайн-фолбэком), engine.js и advisor.js (офлайн-копии расчёта)

```

## Запуск локально (без Docker)

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

```bash
cd frontend
npm install
npm run dev
```

Фронтенд на `http://localhost:5173` сам проксирует `/api/*` на бэкенд (см.
`vite.config.js`). Если бэкенд не запущен — приложение всё равно откроется и
будет работать в офлайн-режиме.

## Запуск через Docker Compose

```bash
docker compose up --build
```
- Фронтенд: `http://localhost:8080`
- API: `http://localhost:8000` (Swagger: `http://localhost:8000/docs`)
